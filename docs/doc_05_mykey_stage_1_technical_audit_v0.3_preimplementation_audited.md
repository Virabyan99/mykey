## 1. Executive disposition

**Retain the OpenBao + PostgreSQL + TypeScript/Hono + React + Traefik OSS + Docker Compose architecture as the initial candidate, not a proven solution.** Use OpenBao's namespace/ACL/KV/token/audit primitives and PostgreSQL's constraints, transactions, locking, roles and SQL functions aggressively. These are the two most underutilized native-capability opportunities. Hono + Zod should form one runtime-validated API contract, and Scalar should be a local, protected, strictly noninteractive reference. The custom application layer should own product authorization, cross-store uncertainty, coherence, limited UX intelligence, and business-specific orchestration — obligations no component can honestly absorb on its own.

**Five existing mechanism blockers dominate the critical path (with additional recovery/version blockers added in §1.4):**

1. **Authentication:** Better Auth's normal `session.token` represents a usable bearer; its 2FA plugin exposes encrypted, viewable backup codes and optional trusted-device flows. The contract instead requires protected session bearer storage, verifier-only backup codes, MFA completion and fresh actual-TOTP use, atomic replay control, private recovery, exact session clocks, and no public bypass routes. There is no sufficient native configuration proof yet. A supported end-to-end extension is **unverified**; treat G-AUTH as STOP for downstream auth UI and release.
2. **Delayed OpenBao effects:** PostgreSQL transactions/advisory locks, pg-boss queues and request timeouts cannot fence an external write already accepted by OpenBao. Durable intent + precise no-takeover policy + stop/drain/attributable reconciliation are necessary. Any protocol that treats a missing read as no effect is unacceptable. Treat G-EFFECT as STOP until proven under forced process/connection death.
3. **Real provider interoperability:** OpenBao 2.7 has a *built-in KMIP seal* **and** a documented *external OVHcloud-specific KMS seal plugin*; OVHcloud also lists OpenBao among products validated with its KMIP service [S08, S25–S26]. These are meaningful evidence of compatibility *paths*, but do not prove our actual key, account, permissions, certificate, restarts or recovery. Native built-in KMIP remains the first experiment, with the extra-plugin path compared explicitly rather than assumed superior.
4. **Consistent and retained backup pairs:** PostgreSQL dumps and OpenBao Raft snapshots are each internally coherent *individually*, not mutually atomic. Restic repository object mutation and R2 retention lock rules must be validated together; a staging full restore and actual lock-aging fixture are indispensable.
5. **Whole-environment resolution:** KV v2 reads separate keys without native cross-key snapshot isolation. A generation/seqlock + admission-exclusion protocol is an application obligation; CLI launch/export must not occur after a torn or truncated read.

**Additional cross-cutting criticality:** authentication credential recovery must not depend on the unavailable MyKey service; no machine bearer is stored in PostgreSQL or log/queue/metrics; Docker Compose secrets are protected *host-mounted files*, not encryption or trust isolation against the host operator. All agent demonstration secrets remain in the trusted executor and its child, not in an LLM's prompt or transcripts. An OpenBao snapshot remains unrecoverable after permanent loss of required external KMIP seal key material, even when OpenBao recovery shares and an encrypted snapshot survive. A PostgreSQL one-database `pg_dump` does not alone prove that the restored installation has the required database roles, grants, extensions, cluster configuration and non-database operational dependencies.

## 2. Method: native-first without feature maximalism

For each FR: (a) identify *enforcing authority*; (b) enumerate native operations and constraints; (c) locate missing guarantees under failure/retry/revocation; (d) compare composition, bounded custom code and additional dependencies; (e) assign a real AC/proof; (f) note operator effort and migration consequences. A utility feature that looks similar but misses a security invariant is a **partial match**, not a solution. A lower package count is not automatically a lower-risk system. Cryptographic implementation must use maintained libraries, even if that adds a dependency.

**Boundary invariants:** OpenBao is authoritative for secret values/history and machine-token validity. PostgreSQL is authoritative for tenant/project/grant/lifecycle/operation data and permitted protected auth records. Neither store's authority substitutes for the other. The public process has no global OpenBao administration capability. The trusted application/host/operator may access plaintext; MyKey is **not** zero knowledge. The credential-consuming child process is a secret-bearing trust boundary. Request/API typing is never a substitute for runtime validation. Browser dashboards and operational telemetry cannot receive sensitive values or raw credentials.

**Prioritization rule:** (1) native capability; (2) simple, demonstrably sound composition; (3) minimal specialized app code; (4) justified maintained third-party library/service. This is an *order of investigation*, not a prohibition on step 4 where a mature library avoids dangerous bespoke implementation. Any component's documented feature may still be rejected if its real authority or recovery surface is too broad.

## 3. Load-bearing capability inventory and optimization findings

### 3.1 OpenBao — exploit the secret engine rather than mimic it

**Potential leverage outcome:** use OpenBao's fixed token-role semantics and native KV version retention rather than maintaining parallel secret/version/token-validity authorities. **Do not** move product authorization or secret-name index into OpenBao KV custom metadata, which lacks transactional business authorization semantics. Do not use an additional secret engine or Transit merely for novelty. Transit may have a future role, but Stage 1 authentication recovery material cannot create a circular dependency on a lost MyKey service.

### 3.2 PostgreSQL — the default coordination and metadata substrate

| Native capability | Employ it for | Why it is not sufficient alone |
| --- | --- | --- |
| Constraints, composite FKs and unique indexes | Tenant ancestry, immutable external keys, idempotency uniqueness, one exclusive effect slot, version tag changes | Constraints do not inspect OpenBao or repair partial effects. |
| Transactions + `SELECT ... FOR UPDATE` | Admit operations, authorize from current rows, serialize projects/archives/issue, atomically write result + audit/outbox | SQL commit cannot atomically commit an OpenBao write. Reauthorization and actual lock order still necessary. |
| Transaction-scoped advisory locks | Deterministic per-key / per-environment exclusion during SQL admission, bounded contention | A session/transaction lock vanishes when its connection is lost, **not** when a remote OpenBao request is guaranteed finished [S09]. Do not equate advisory locks with fencing. |
| Durable operation/effect-slot tables | Crash-visible state, idempotent replay, ambiguous-result quarantine; long-lived exclusion without expiring takeover | Requires explicit executor identity, kill/drain boundary and evidence-based reconciliation. No lease-only automatic takeover. |
| SQL roles, schemas, `GRANT`, append-only tables/functions | Separation of API/provisioner/backup/maintenance/audit writers | Runtime `INSERT` privilege may still allow forged event fields unless fixed-schema insert path validates actor, target and correlation. Database administrators remain trusted. |
| Row-level security (optional defense-in-depth) | Potential second guard for owner-scoped views and tenant metadata | Owners / BYPASSRLS can bypass; pooled application connections and session variables can be mis-set; RLS policies themselves can race with mutable referenced auth rows. Do **not** make RLS a substitute for explicit current application authorization. Adopt only with two-tenant bypass tests [S10]. |
| `pg_dump`, snapshots | Internally consistent PG backup, schema export/migration rehearsals | Independent OpenBao snapshot is *not* the same logical instant. Backup read identity must be complete, not RLS-truncated. `pg_dump` alone does not include cluster-global roles/privileges; plan `pg_dumpall --globals-only` or a documented, verified role/bootstrap reconstruction with least-privilege revalidation. If exporting cluster globals, protect potential password verifiers and revoked identities as sensitive material, and do not revive them after quarantine restore [S11, S40]. |
| SQL aggregates, indexed events | Owner dashboards: counts, timelines, credential expiry and bounded error-category trends | Data provenance, freshness, tenant filtering and retention still need schema/API constraints. No ClickHouse, Redis or general telemetry platform needed for Stage 1. |
| `LISTEN/NOTIFY` (optional) | Lightweight invalidation hints for owner UI/queue wakeups | Notification is not durable task or authorization authority. Poll/status via durable SQL remains source of truth. |

**Priority simplification:** a single reviewed transactional metadata store handles authorization, replay, jobs, limited analytics and status. pg-boss is an in-Postgres library and only delivers work; it is not the operation ledger, exactly-once coordinator or backend fencing mechanism. A separate Redis/cache/message broker is not justified for this scope.

### 3.3 Traefik OSS — TLS/edge guardrail, not product policy engine

Native routers, services, TLS options, HSTS/security headers, transport trust, request size/connection controls, middleware chain, `ping`, and basic access metrics/logging are valuable. A single origin for SPA/API avoids ordinary CORS problems but **does not remove CSRF obligations**. Do not introduce `ForwardAuth` just to protect Hono routes already using Better Auth: it adds authorization round-trips while failing to replace product resource grants. Edge rate limits supplement — not replace — account/factor-specific atomic PostgreSQL throttles. Traefik `retry` on mutating or secret-bearing routes is unsafe unless a specifically proven idempotent end-to-end protocol tolerates it; default **off**. Avoid body-buffering middleware that writes secrets to disk, and disable proxy request/response body logging. **Edition/version correction:** In Traefik Proxy 3.6, OSS `rateLimit` documents an optional Redis backend for distributed enforcement; Traefik Hub separately publishes a `distributedRateLimit` offering. The two must not be conflated. This does not make Redis appropriate for a one-proxy Stage 1 [S13, S27]. Distinguish other verified OSS functionality from Hub/API Gateway features. Be explicit about trusted-forwarded headers, TLS certificates, proxy/API internal mTLS and DNS-01 vs TLS-ALPN tradeoffs; do not expose the dashboard or private health routes [S12–S14]. On all secret-bearing input routes, Traefik's `buffering` body-size feature must be examined for possible disk spooling before adoption [S31].

### 3.4 Docker Compose and host OS — exploit isolation, do not overclaim it

Employ Compose healthchecks, dependency order, per-service networks, capability dropping, read-only root FS, `no-new-privileges`, UID/GID controls, tmpfs, `pids_limit`, memory/CPU reservations/limits (verify Compose + runtime interpretation), and service-scoped `secrets` mounts. Supply-chain policies use signed/digest-pinned images and scanned base/OS layers. Maintain staging with same Compose release definition but isolated accounts/credentials.

**Boundary:** Compose `secrets` are mounted files; with file-backed Compose deployments their confidentiality depends on host permissions and access to source file, not Docker Swarm's encrypted Raft secret model. Compose healthchecks establish process-specific readiness, not transaction consistency or backup recoverability. A container sharing a kernel with the trusted host is not a hostile-code sandbox; the Stage 1 agent harness must execute in a *separate trusted runner boundary* with a fixed allowlisted command and no arbitrary agent-controlled code in the secret-bearing process [S15]. Use simple hardening only after probing real OpenBao image UID, Raft data path, KMIP cert reload and postgres durable volume operations.

### 3.5 Better Auth — leverage proven login primitives but gate its extensions

Better Auth natively supplies password auth, session records, Drizzle integration, TOTP challenges, recovery/backup-code routes, rate limiting, and revocation helpers. These provide clear implementation leverage **only if the configured public route set and underlying data model satisfy MyKey's stricter contract.** The documented database schema contains a `session.token`; plugin features include *encrypted/recoverable* backup-code storage, server viewing of backup codes, MFA disable paths and `trustDevice` options. Native plugin backup codes cannot be presumed verifier-only; default session freshness cannot be interpreted as actual TOTP freshness; cookie caching can delay revocation if used without database checks [S16–S18].

**Candidate A — preferred to test first:** prove a fully supported Better Auth custom adapter/plugin boundary that consistently transforms bearer storage and overrides/forbids every disallowed endpoint, uses SQL-atomic recovery code/TOTP step consumption, rotates session on elevation, enforces custom idle/absolute/freshness policy, and handles reset while preserving legitimate supported flows. Require interception proof for reads/writes/refresh/list/revoke, not a demonstration of just one sign-in path. Maintain the native password verifier and supported API where possible.

**Candidate B:** retain Better Auth for password verification and tightly constrained primary auth but implement a separately maintained, well-tested minimal *product session/factor layer* when A's adapter is not dependable. This trades complexity for an explicit security boundary; it needs independent review and likely increases the 400-hour estimate. Never silently implement insecure session handling or cryptography. **Candidate C:** choose another mature maintained auth platform whose storage and lifecycle can meet all FRs, only through a documented P-03/Doc 04 change; do not evade the functional contract by adopting weaker defaults.

**Stop/go:** Prove G-AUTH with an exact-pinned auth route inventory, schema and raw DB inspection, two concurrent API processes, adversarial factor/replay tests, no token in DB dump/logs, and operator reset after actual restore. If the extension is unsupported, stop dependent auth work and choose B/C via formal review; do not accumulate local hooks that happen to pass only the happy path.

### 3.6 Hono + TypeScript + Zod — make contracts shared, not fictional

Use Hono routing/middleware for transport and error gates; Zod (or proven Standard Schema integration) for actual parsed request/response validation; shared discriminated result schemas for `active`, `archived`, `uncertain`, and error variants; generated OpenAPI from the *same* route metadata. Use Node HTTP adapter and explicit body-size/timeouts/trusted proxy config. Generated typed RPC clients can reduce interface duplication, but a typed API is compile-time ergonomics, not runtime defense: validate **received bytes** in browser and CLI and verify complete content length/checksums for whole-environment reads. Restrict accepted JSON keys/selectors, audit data and error serialization. Per-route state/permission checks stay in application handlers; generic auth middleware alone does not implement the matrix. Avoid redundant controller frameworks, an extra GraphQL server, code generators unrelated to the shared contract, or general orchestration infrastructure [S19].

### 3.7 React + selected UI stack — rich DX without sensitive-data retention

Compose a single responsive owner workspace from existing shadcn/Base UI and TanStack patterns; use browser-accessible tables, status chips, narrow charts using existing components/semantic SVG, and backend aggregate endpoints. Scope all client caches to **nonsecret metadata**; never store reveal/import/credential issuance responses in TanStack Query, Redux/Zustand persistence, error monitoring or browser storage. Reveal values only in an isolated short-lived component state (no claim of memory zeroization), with explicit user copy and automatic expiry. React Strict Mode may re-run effects in development; never start a sensitive mutation in a mount/effect. Treat all transitions as server-verified, not optimistic success. Aesthetic ambition should serve actionable diagnoses and trustworthiness rather than chart count [S20].

### 3.8 Scalar — substantial DX, without the security cost of “Try it”

Ship pinned, **locally bundled** Scalar API Reference from a protected same-origin route with a sanitized product-only OpenAPI description, good error/status schemas and safe examples. Disable request execution (`hideTestRequestButton` or exact pinned equivalent), interactive API-client launch, remote proxy/default demo endpoints, remote plugins/fonts/assets and runtime telemetry. Scalar API client is an excellent development tool, but exposing live secret-mutating “try it” in the user-facing Stage 1 reference is a poor match for the strict local-read-only contract. Scalar configuration options change; compile a supported-options inventory on pinned package and inspect emitted network requests. Current upstream configuration declares flags to hide the test-request button and disable document downloads [S21]. Documented local browser security must be verified by CSP/network tests, not inferred from a configuration flag.

### 3.9 Selected supporting technologies and why they remain

- **Drizzle ORM/Kit + `pg`:** type-safe app queries, reviewed migrations plus custom SQL for roles, constraints, partitioning, functions and pg-boss schema; ownership of migrations belongs to one defined deploy step. No duplicate application Kysely layer.
- **pg-boss:** persistent Postgres-backed scheduling/retries for workers **after** durable operation admission; no unexamined duplicate effects or unrestricted worker migrations.
- **Zod/OpenAPI tooling:** request *and* response runtime contracts, including incomplete-body detection in CLI. Avoid duplicate independently handwritten types.
- **Restic + Cloudflare R2:** candidate backup encryption and durable off-host storage. The existing technical specification's *independent Restic repository per capture pair archived as immutable R2 objects* is a candidate mitigation of mutation-vs-object-lock conflict; prove repository validity, immutable manifests, physical retention, per-object delete results, real lock-aging, measured total storage/API costs and oldest-pair restore before selection. Do not reintroduce a shared mutable Restic repository under mandatory bucket locks by assumption [S22–S23].
- **OVHcloud KMS:** candidate external seal authority. Verify native KMIP operations, certificate provisioning, quotas, key version retention, provider API permissions, actual availability and recovery prerequisites. Provider-specific pricing and SLA remain unchecked until account evidence.
- **A mature JOSE/cryptography implementation:** conditionally justified for authenticated session/TOTP-seed encryption if Better Auth extension requires it; avoid custom primitives. **Do not** persist any machine token even encrypted.
- **External health/probe + alert delivery:** minimal off-host independence; keep full telemetry console/analytics pipeline out of Stage 1.

### 4.1 Concurrency and state coherence: proposed proof-level protocol, not final spec

At mutation admission, lock the relevant PostgreSQL resource ancestry and durable effect scope, re-evaluate current authorization and state, persist a nonsecret intent and expected OpenBao metadata, and reserve a non-expiring execution slot. Record dispatch *before* initiating a backend action. A completed backend effect is verified and the terminal state plus new state tag committed. A transport timeout or process death may leave `uncertain`; no other executor may assume absence until a safe exclusion boundary is established. In particular, a transaction lock release or pg-boss retry is **not** proof a prior HTTP request did not reach OpenBao. Stop the old executor/connection at a host/process boundary where it cannot issue new effects; account for possibly accepted requests and correlate backend audit/version/token accessors. If attribution is insufficient, leave scope blocked. Document 06 must formalize different reconciliation evidence for KV write, delete, undelete, token creation, accessor revocation, provisioning, and archive.

For complete-environment reads, use a monotonically changing *environment mutation generation* and an admission protocol that accounts for **every relevant mutation and ambiguous effect**. A reader must establish a stable serving generation, enumerate bounded names, fetch current values under the presented machine token, verify no missing/deleted/review/mismatched entries and recheck generation and policy before releasing the *complete* result. Do not treat optimistic generation recheck as sufficient if an already-dispatched backend request can finish after the recheck; that case must remain blocked by the durable effect barrier. Document 06 must prove nonstarvation, size bounds and fail-closed transport handling.

Archive begins with resource state denial at a transactionally authoritative admission boundary. It must block concurrent environment creation and issuance, drain/reconcile admitted mutations and unknown tokens, revoke all affected token accessors and verify backend denial. Native TTL expiry can be an additional guard, **not** the exclusive proof of immediate revoke. Reactivation restores no previous token.

### 4.2 Authentication lifecycle: operationally complete, not stock MFA

A verified password may start only a restricted login challenge; a product session is authorized only after an *actual* allowed second-factor challenge completes. Account-enrollment state, successful TOTP step, session birth, last explicit user activity, absolute expiry, credential epoch and fresh TOTP verification must be represented and transactionally checked. A recovery code is a single-use high-entropy verifier, never a recoverable encrypted backup code; user-visible regeneration is one-time delivery. Password or MFA reset is operator-triggered only, uses a one-time token with private generation, moves the account to recovery-pending and invalidates old sessions/challenges. After restore, old authentication material is untrusted even if backup decryption succeeds. Test native handler semantics before accepting any alternative session architecture.

### 4.3 Security boundary review

**Enforce in OpenBao:** namespace isolation, machine token scope and validity, version retention, native audit; **in PostgreSQL:** membership/grant/resource states, operation ledger, nonsecret audit/metadata, app authentication-phase state; **in Hono:** per-request current authorization, CSRF/origin, body limits, API scope, coherent secret delivery; **in Traefik/host:** TLS, exposed network surfaces, trusted headers, basic DoS controls; **in CLI:** complete-response verification and no-shell execution; **in React:** short-lived authorized reveal and no secret caching; **in independent operator tooling:** bootstrap, provisioning, quarantine release, credential recovery, snapshots, cross-store reconciliation. A single operator may hold multiple responsibilities, but its web role is not an infrastructure administrator identity.

**Unaffiliated agent requests:** an agent sending a fixed instruction through a trusted executor has **no right** to arbitrary CLI arguments, child command, credential files or environment selection. The executor chooses the approved fixture from its own configuration, and the credential-bearing runtime remains trusted. You cannot guarantee secrecy from an agent permitted to execute arbitrary code inside that same runtime; state this limit in the published product claims.

### 4.5 Critical threat-boundary choices that cannot be deferred to code review

1. **Public API credential residency:** A per-org issuer token held in a public API process is a compromise target even if it is not a root token. Evaluate whether issuance can be performed by a separately permissioned private process without making the application fragile; if co-resident, explicitly state blast radius and enforce fixed OpenBao token roles plus authentication/freshness/audit/transactional admission.
2. **Credential exposure to automation:** A prompt-injection-resistant LLM prompt is not a credential vault. The bounded agent demonstration must keep plaintext retrieval and child execution entirely in the trusted runner, not a programmable agent-controlled shell. An agent allowed to run arbitrary code in the secret-bearing environment can exfiltrate secrets; the product must not claim otherwise.
3. **Backend authorization and historical versions:** A raw OpenBao token with KV v2 read permission may accept historical-version selectors on `data` reads. `keys/run/export` product APIs enforce current-only semantics. Access to OpenBao itself must remain private, with no assertions of native current-only enforcement under arbitrary direct token use.
4. **Audit accuracy under failure:** SQL and OpenBao audit logs may be incomplete, divergent or lagged after a crash. Attribute only what is demonstrably known; display pending/unknown states and never infer success from no observed failure.
5. **Disaster recovery trust:** All restored sessions, factor state, machine/runtime tokens and issued-but-not-inventoried credentials require explicit invalidation/reconciliation. Service reopen must depend on trusted off-host recovery controls rather than fields restored from PostgreSQL.

## 7. Effort, calendar risks, and a disciplined scope valve

The 400-hour target is a **scoping objective, not an established estimate**. A work-product cannot be certified from the count of FRs: one FR may require several weeks of threat modeling and fault injection while another is native configuration. Document 07 must estimate **implementation + integration + negative testing + proof fixtures + independent security review + deployment + recovery + user documentation + four-week correction work**, using bottom-up mini-project estimates with likely/high uncertainty and identifying prerequisites. Calendar time for aging bucket-lock fixtures and later field observation is independent of engineering hours; changing object timestamps does not remove real-aging proof time. **AC-1.36/AC-1.44 are release-due** unless the controlling records explicitly amend them; therefore it may be impossible to authorize controlled use in the intended engineering-start week. This is a release timing constraint, not a reason to weaken the retention requirement. Independently restorable full daily pairs must be costed against cumulative bytes and operational/API expense.

Early complexity alerts are concentrated in Better Auth hardening, all-or-nothing mutation and snapshot protocols, real KMS integration, independently restorable locked backup pairs, and four-target CLI packaging. None should be papered over with a generic 10% contingency. Independent review and real-provider setup effort are real tasks. **A likely 400-hour overrun is a risk to report**, not a reason to cut tests or security.

If the bottom-up result exceeds 400 hours, record a scope-reduction proposal that removes a **whole capability slice** and its entire lifecycle, negative cases, documentation and user promise (and corresponding approved FR/AC/PO updates), or approve a justified budget overrun. Possible *discussion candidates only* include simplifying archive/reactivation *as a complete removed workflow*, limiting plaintext export *as a wholly excluded feature*, or narrowing supported CLI distribution targets *with conspicuous public claims*. None is approved by this audit, and none can be removed silently: the current 102-FR candidate remains intact. Do **not** remove MFA/secure recovery, authorization, backend revocation, complete-value delivery, crash uncertainty, auditing, TLS, quarantine, backup-restorability or truthful DX while still claiming the current product. Nor may later stages inherit broken or half-built included functionality.
