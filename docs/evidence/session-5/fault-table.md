# Fault table — machine credentials (Run 5.2 Task B)

AC-1.40 SPIKE_PASS — losing the response at each boundary of issuance and revocation never leaves a working token that nobody knows about once the operator has run, never shows `revoking` as revoked, and no replay creates a second token.

**Setup:** `tests/fault/credentials/` on the local stack. Two API processes: the in-process one, and a child that really dies (the fault `crash` is SIGKILL inside the hook). Both reach OpenBao through the TLS relay. Every case ends with `expectCatalogMatchesBackend`: every machine token OpenBao holds for the environment is the accessor of an `active`, unexpired row, every such row's token exists, and no advisory lock is left. Then the environment is cleared. Tokens are compared by booleans and counts only. Every run of `reconcile-credentials` is checked for accessors in its output (none).

**Result:** 11 / 11, three passes in a row (`pnpm exec vitest run --project integration --maxWorkers=2 tests/fault/credentials`, 15 Nov 2026), then a fourth with the verbose reporter (57 s).

**Mutations** (each reverted at once):

- `reconcile-credentials` no longer links a found token to its issuance: 5 issuance rows failed.
- An unproven revocation puts the credential back to `active`: the "drop" revocation row failed.

## Deviations from the plan's table

- **"Holds the request 10 s past the deadline" is 3 s past it (8 s in all).** OpenBao never served a request that reached it more than about 10 s after its connection opened: with a 15 s delay no token ever appeared. The cause is probably the listener's read-header timeout. A late create is possible only inside that window. A first variant held every request and released them together about 13 s after the create's connection opened, because the API also waited for its issuer session's `revoke-self`. It made no token, from that window or because `revoke-self` landed first. The case therefore delays every request by 8 s (`delayRequests`): the create lands at 8 s, and the `revoke-self` sent at 5 s lands after it.
- The sweep is triggered by aging the operation's heartbeat past 120 s and calling `sweepCredentials`, not by waiting for the API's 30 s tick.

# Fault table — archive (Run 5.3 Task D)

AC-1.11 SPIKE_PASS — an archive interrupted at any of its three fault points is finished by the other process's tick with no operator; an issuance racing an archive never leaves a usable token; no environment is `active` or `pending` under an archived project; the request and the tick driving one archive at once finish it once.

**Setup:** `tests/fault/credentials/archive.test.ts`, same two processes as above. A child started with `archiveTick` runs `continueArchives` every 200 ms (10 ms in the last row) with a stale time of 0, as the API's sweep does. The child that is killed has no tick. Tokens are compared by booleans and counts only.

**Result:** 6 / 6, three passes in a row (`pnpm exec vitest run --project integration tests/fault/credentials/archive.test.ts`, 15 Nov 2026, 129–134 s each), with no unhandled error.

**Found and fixed:** the first run of the create race answered `503 dependency_unavailable` to a create. Archive admission locked the target project FOR UPDATE and then the organization FOR SHARE (in the recheck). A create updates the organization row first (the list generation) and then takes the project FOR SHARE, so the two deadlocked. Archive and reactivation admission now take `lockParents` (organization, project, environment) before anything else, the order of every other admission. Afterwards: four runs with no 503.

**Deviation from the plan's table:** the plan's 0–30 ms offset never reached the issuance's finalize. With it all 50 issuances answered `409 state_conflict` in three passes, so the case where a 201 is answered and the archive must revoke it never ran. The offset now spans the issuance's measured duration, and the test asserts that both orders occurred. The create race uses a signed offset for the same reason: with 0–30 ms the create came first in 59 of 60 rounds.
