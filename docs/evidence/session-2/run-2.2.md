## Deviations and decisions

- **`explicitMaxTtlSeconds` is 0, not 2,592,000.** The brief expected the lookup to show the role's cap. On 2.7.2 a token minted from the role reports `explicit_max_ttl: 0`; with `explicit_max_ttl: "9000h"` in the request it reports 32,400,000 (the request's value) while its TTL is still cut to 2,592,000 and the answer warns `using the lesser value of 2592000 seconds`. The cap is proven by behaviour instead: `ttl: "2592001s"`, `explicit_max_ttl: "9000h"` and `ttl` + `explicit_max_ttl` of 9000 h all yield `creation_ttl` 2,592,000 and a TTL within 5 s of it; the token mount's own maximum is 768 h, so only the role's 720 h explains the value. The shape test asserts the observed 0 and checks `creation_ttl` and `expire_time − issue_time` instead.
- **`policies: ["runtime"]`** is 400 (`must be subset of the role's allowed policies`), one of the two statuses the brief allowed; the accessor list of the namespace is unchanged, so no token was made. `["default"]` and `[machine, "default"]` give the same answer.
- **Refusals are 400 with an error text, not 403**, for `period` (`root or sudo privileges required to create periodic token`) and `id` (`root or sudo privileges required to specify token id`).
- **`renewable: true`** is proven by behaviour as well as by lookup: the root token's `renew-accessor` of the token answers 400 `invalid request` (bare text; the control — the same request for a renewable 120 s token — answers 200 and extends it).
- **`auth/token/create/unknown-role`**: the role did not exist, so the root control first answered 400 `unknown role unknown-role`. The test writes the role (outside the `machine-env-` family) for the duration of the test so the root control mints; the issuer stays 403. A nonexistent name inside the family is 400 `unknown role …` for the issuer, recorded in `what the issuer may still choose (D-18)`.
- **Added beyond the brief:** `what the issuer may still choose (D-18)` (shorter TTL, `num_uses`, `meta`, `display_name`, omitted `policies` are accepted; `entity_alias` is 400), the B-role attempt through the root namespace with B's path prefix, and an `explicit_max_ttl` attempt without a raised `ttl`.
- **An expired token's accessor lingers.** Before the fix, `the token outlives its issuer` failed in 2 of 4 full `test:integration` runs (`expected 200 to be 400`; never in the focused runs, where the stack is idle): the 3-second issuer was already refused (403), but the root token's lookup of its accessor still answered 200 for a moment, until the expiration manager removed the entry. The test now asserts the machine token reads right after the issuer is refused, then polls (30 s deadline) until the lookup answers 400 `invalid accessor`, and reads again. Recorded in D-18 for the inventory runs.
- **Lookup after revocation or expiry** is 400 `invalid accessor` (the typed client returns `invalid`, status 400). Revoking an accessor that no longer exists answers **200**.
- **Same read with B's header:** the seed was also written at A's path inside B, so the control (B's runtime token, same request) answers 200 and the machine token's 403 is a denial, not a missing object.
- **Timing.** The 3-second issuer and the 2-second token are watched with a bounded poll (200 ms steps, 20 s and 15 s deadlines). The short token test also asserts it was not refused earlier than 1.5 s after the issuance started, and still refused at 3 s.
- The registry is not edited in this run (ruling R6).
