### 2. Answers to the seven questions

1. **What listens beyond HTTPS and WireGuard:** from the internet, only the DHCP client on UDP 68 (R6-5) and rate-limited ICMP. From the VPN, only SSH on 22. Inside the host: PostgreSQL 5432 on mk-db; OpenBao 8200/8201 on all of its interfaces (mk-bao and mk-kms); the API on 8443 and 8444 on all three bridges (R6-2); Traefik on 8443. With the table missing at boot, more is exposed (R6-4).
2. **What each container reaches, and with which rights:**
   - edge (uid 65532): API on any port via mk-edge, the ACME set on 443, the resolver on 53 (R6-3). It holds the ACME volume and the host CA certificate.
   - api (uid 1000): PostgreSQL as any role (R6-7), OpenBao, the provisioner, no egress. It holds the `api_runtime` password, the runtime and issuer AppRole credentials, the key rings and its TLS key.
   - openbao (uid 100): the KMS on 5696 and the resolver on 53. It holds the whole KMS directory (R6-8).
   - provisioner and postgres: their bridges only, no egress.
   - pki-init: root with CHOWN, DAC_OVERRIDE and FOWNER, no network.
   - ops jobs and okms: the host's full reach (R6-1).
   - backup: pg_dump on mk-db, restic with no network.
3. **What the edge's access log holds:** Traefik's common log format goes to journald: client IP, time, method, the full path with query string, status, size, Referer (page paths, so secret names), User-Agent (`secrets/<version>` from the CLI), router, backend URL and duration. No headers, cookies or bodies. Reset tokens travel in the fragment, which is never sent; machine and session tokens travel in headers and cookies, which are not logged. Query parameters hold only name prefixes, cursors, ids and filters. Nothing else of value reaches it. Its retention is bounded by journald alone, not by the product, and it is outside the audit purge and archive.
4. **Is the exposure written in `.trivyignore.images` true:** yes, as a statement of who can reach each image. The real exposure is probably narrower than written for Traefik and live for OpenBao, though OpenBao is not public. I could not check this against the advisory itself (it postdates what I know):
   - **OpenBao:** reachable from the api, provisioner, ops containers and host processes, never from the internet. OpenBao wraps request bodies with MaxBytesReader to enforce `max_request_size` (not set, so 32 MiB), so the flawed function is plausibly on its path.
   - **Traefik:** public on HTTP/1. Traefik calls MaxBytesReader only in its buffering middleware, which this edge does not configure, so it is plausibly not on the path.
   - **Smaller inaccuracies:** the restic note leaves out that the image is also okms's runtime on the host network (okms is a Go binary, so the listed Alpine library CVEs are plausibly unused). The node note is now stronger than written, because npm is removed from all three of our images.
5. **Is anything unpinned:** yes, though no image is.
   - Host apt packages (R6-10) and the Trivy vulnerability database.
   - In `probe-watch.yml`, `runs-on: ubuntu-latest`.
   - In CI, `setup-python` `"3.12"` (patch version floats) and the apt dependencies of `playwright install --with-deps`.
   - Every image (by digest), every Action (by SHA), npm (exact) and pnpm (with hash) are pinned.
6. **Can the probe's state, a heartbeat or an alert carry a secret:** no.
   - The heartbeat has a strict schema: booleans, counts, ISO times, regex-checked certificate and unit names, and a boot id of at most 64 characters.
   - An alert names only host, condition, kind and time.
   - The only secrets on that path are the tokens themselves: the heartbeat bearer in a root-only curl config, and the Telegram bot token in the Worker's environment.
7. **Does a workflow hand a secret to code from a pull request:** no.
   - `ci.yml` uses `pull_request` (not `pull_request_target`) and references no repository secret. `github.token` is used only in the dispatch-only cli-matrix job, with `contents: read` and `persist-credentials: false`. Pull-request values go through `env`.
   - `probe-watch.yml` holds the three secrets but runs only on schedule or by dispatch.
   - Caveat (plausible): the secrets are repository-level, not scoped to an environment on `main`. So any writer's branch, agents included, can read them by editing a workflow. This is GitHub's default behaviour.

**Stated limits:** `known-limits.md` states nothing about the network. D-21's own "open weakness" (egress allowed by address, not by name) is missing from it, and so are the DNS channel (R6-3) and R6-1. The limits it does state for my area are correct.
