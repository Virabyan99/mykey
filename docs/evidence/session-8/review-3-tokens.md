### 2. Answers

1. Stored or logged: none found. The token is a local of `issue.ts` and the 201 (`no-store`). It is not on the operation result, an audit row, a log line or the request log (route pattern only). Traefik drops headers by default. OpenBao's audit device keeps HMACs. `surfaces.test.ts` searches every surface for it.
2. Twice or two: none. There is one create per marker. The replay answers `credential_not_replayable` and never the token. Two issuances in one environment are serialized by the advisory lock and by the unique index on `issuing`/`needs_review`. Nothing retries.
3. Untracked token: yes, until the operator acts. An unknown create leaves `needs_review` with no accessor; the token is found again only through its `meta.operation_id`. R3-3 is the case where the accessor was known and dropped.
4. "Revoked" before proof: none. `revoked` needs a lookup that answers 400. Without proof the state stays `revoking`. A definite create refusal, or `--executors-excluded` finding no token after a full listing, is labelled `revoked` without a per-token proof, by design.
5. Archive race: none for recorded tokens. The row locks plus `ParentsClosed` lead to a withdraw. `needs_review` and `issuing` rows block the finish (`openCredentialWork`). For off-book tokens, see R3-2.
6. Machine token scope:
   - history: yes, directly in OpenBao only (the known residual, understated: R3-5);
   - another environment: no;
   - renew itself: no;
   - make a token: no, except response-wrapping tokens (R3-4).
7. The issuer, beyond issuing:
   - it can mint 30-day tokens for every environment of its organization, archived ones included;
   - it can look up and revoke any token of its namespace by accessor;
   - it can read the machine policies and token roles;
   - all of this is tested as hostile in `authority.test.ts:624,652`; the gap is R3-2.
8. Lockout off: no finding.
   - The cost: unlimited online guessing of random 128-bit secret ids from the private network (CIDR-bound where set), with no OpenBao rate-limit quota and no alert on failed logins.
   - The gain: it removes a denial of service, since role ids are not secret.
   - A doc to fix: CLAUDE.md "Things already learned → OpenBao → User lockout" is stale, and its pointer to known-limits.md now points at nothing.
9. Custody root token: R3-1, Medium. It does not block controlled use with real, non-critical secrets: a compromised workstation is already total through SSH with sudo and the API's secret ids on the host. The smallest change that would remove the finding:
   - mint one orphan token with an explicit max TTL (for example 30 days, non-renewable) and either a scoped `operator` policy or `root`, and put it where `root_token` is in the custody file;
   - revoke the init root token;
   - take `recovery_keys*` out of the workstation file (keep the share in the password manager and on the host only);
   - renew the token through `generate-root`.

### 2. Answers that change

3. **Untracked token:** yes, until the operator acts. An unknown create leaves `needs_review`, and the token is found later by its `meta.operation_id`. In two more cases the accessor was known and thrown away: a finalize that fails in the process, and a late executor after the sweep (R3-3).
4. **"Revoked" before proof:** still none. `revoked` is set only after a lookup answers 400; in every other case the state stays `revoking`. Two additions:
   - A definitely refused revocation stays `revoking` with no alert and no re-drive (R3-6).
   - Machine authentication refuses any credential that is not `active`, a `revoking` one included (`apps/api/src/pipeline/machine.ts:184`). No test sends a `revoking` but still-live token to a machine route, though; `authentication.test.ts:189` tests only a credential already `revoked`.
5. **The issuer, beyond issuing:**
   - It mints 30-day tokens for any `machine-env-*` role of its organization, archived environments included (R3-2).
   - It looks up and revokes any accessor of its own namespace. The runtime's login token is included, though production's runtime uses inline authentication and stores no token (`inline.test.ts:73`).
   - It cannot reach another namespace: OpenBao answers 500 "different namespace" (`authority.test.ts:799`).
   - **Combined with the provisioner it holds every right in the namespace.** The provisioner can write any policy text under `machine-env-*`, including on an existing environment's policy, which instantly widens every live token of that environment. This is recorded as an accepted hostile case (`authority.test.ts:879`). Detection rests on the provisioner's own sweep, `verify-organization`, and the digest check at reactivation (`reactivate.ts:134-140`). The archive never checks it.

The answers to questions 1, 2, 5, 6, 8 and 9 are unchanged. On question 5, `reactivate.ts` checks every stored accessor (400) but never lists the namespace, which is consistent with R3-2.
