### 2. Answers

1. **Partial, cut or inconsistent answer:** A cut, short, oversized, encoded, non-JSON, incomplete or miscounted answer starts nothing and writes no file. An export that is killed or crashes can still leave a partial file at its final name (R5-1), and `run` checks values less strictly than `export` (R5-9).
2. **TLS and redirects:** Verification cannot be switched off, and no redirect is followed (the token is sent only on the one request that answered 3xx, to the API itself). Trust can still be widened by `NODE_EXTRA_CA_CERTS` and, plausibly, `OPENSSL_CONF` or `NODE_USE_SYSTEM_CA` (R5-2).
3. **Where the token is:** Not in arguments, logs or history, and not in the child's environment. It is in the CLI's own environ for the child's whole life, and the child can read it there (R5-6). It reaches the `getconf` subprocess (R5-4), and a SIGUSR1 can expose it to an inspector (R5-3).
4. **Export and files:** A symlink at the target is refused (`O_EXCL|O_NOFOLLOW`), a pre-existing link in the path is refused, and an existing file is never overwritten. A partial file can be left on a kill or crash; it is 0600, so readable only by the owner (R5-1). There is a race through a writable ancestor (R5-8).
5. **Signal forwarded twice:** Yes, in some cases: a group-wide signal without a terminal (systemd, `timeout`), or Ctrl-C with stdin redirected. In the opposite case, a signal sent only to the CLI's pid with a terminal on stdin is swallowed (R5-5).
6. **Installer verification:** Yes, for the CLI and Node archives, against sums written into `install.sh`. But `install.sh` is checked only against a `SHA256SUMS` from the same release, `secrets-launch.sh` is checked by nothing, and a re-install verifies nothing on disk (R5-7).
7. **Error prints a value:** No. Messages are fixed text; `code` (an enum) and `requestId` (a UUID) come only from a parsed envelope; any other error prints a generic line; and `cleanup required:` prints only the user's own path.
