## Corrections

Page text changes follow P-145 (a change under `apps/web` makes `host-v0.8.1`); document changes change nothing of the candidate.

**C1 — known-limits.md:90 (also on the Help screen).** Claim: "A segment cannot be deleted before then, even by the owner." True: no token a host holds can delete a locked segment or change a lock rule (D-16:9, 25, 41: seven object tokens got 403 on a lock change). But `mykey-r2-admin`, on the owner's workstation, sets lock rules through the Cloudflare API (D-16:13, 39; `credential-custody.md:10`), so an administrator can remove the rule and then delete. FR-1.102 forbids this claim. Proposed: "**The audit archive is locked.** Staging's for 30 days, production's for 365. No host token can delete a segment or change the lock before then; the owner's account token `mykey-r2-admin` can remove the lock rule, and with it the protection (Run 6.2, D-16)." A document change, but the Help screen bundles this file at build (`help.tsx:8`), so the page changes too. Which P-145 rule applies needs deciding: the file is under `docs/`, but it ends up inside the `apps/web` bundle.

**C2 — backup.md:64.** Claim: "From then on every object under `pairs/` stays 30 days, test pairs included." Same as C1: the rule can be removed by the account administrator (D-16). Proposed: add "…test pairs included, unless someone with the account token `mykey-r2-admin` removes the rule (D-16)."

**C3 — backup.md:96.** Claim: "R2 holds only ciphertext and signed records." True for the pairs bucket: the bundle is Restic-encrypted and `eligible.json` signed. The audit archive in R2 (`audit.md:134-136`) holds gzipped audit rows and OpenBao audit files, not encrypted (`apps/ops/src/commands/audit-archive.ts` has no encryption); they hold no secret value. Proposed: "The pairs bucket holds only ciphertext and signed records."

**C4 — restore.md:55.** Claim: "Run the same command again: it starts from step 1 and does every step again." True only before step 4: after the OpenBao step the target's root token is gone, and a rerun needs OpenBao wiped and initialised again (known-limits.md:108, Run 8.5 R4-3). Proposed: add "This holds until step 4. After the OpenBao step a rerun needs OpenBao wiped and initialised again (known-limits.md, R4-3)."

**C5 — apps/web/src/screens/help.tsx:117-119 (page text).** Claim: consumer-local steps 1–6 "check every file it downloads before it installs anything." False for `secrets-launch.sh`: `SHA256SUMS` covers the release's own files only (`infra/release/cli/build-release.ts:7`), the wrapper is fetched by tag with no sum and installed in step 3 (`consumer-local.md:14-35, 57`; known-limits.md:67; review-5-cli.md R5-7). Proposed: "…steps 1 to 6: it checks the CLI and the Node it installs against their sums; the launch wrapper has no sum (see the known limits)."

**C6 — consumer-local.md:5 and consumer-deploy.md:5.** Claim: every block marked `<!-- rehearsed … -->` is run, in order. Blocks marked `rehearsed: provided` (step 1's downloads, step 5's or step 2's variables) are not run: the test places the working-tree release and its own variables instead (`tests/consumers/runbook.test.ts:315-325, 432-436`; review-5-cli.md R5-7 "the consumer test never downloads it"). Proposed: "…is run, in order, … except blocks marked `provided`, whose result the test supplies itself (the downloads of step 1 and the variables)."

**C7 — consumer-local.md:102.** Claim: issue "through the API until the web workspace exists". The workspace exists since Session 7 and has the Machine credentials screen (`apps/web/src/screens/credentials.tsx`). Proposed: "The owner issues a token on the workspace's Machine credentials screen, or through the API ("Issue" in `machine-credentials.md`)."

**C8 — workspace.md:59.** Claim: "No GET of the API changes a row." The test it cites compares every table except `app.rate_limit` and leaves out the machine GET (`tests/integration/browser-security/origin.test.ts:44-46, 90-91`); `GET …/machine/…/keys` writes a `machine.keys` audit row and `last_used_at` (`apps/api/src/pipeline/machine.ts:121-122`). Proposed: "No GET a browser session can send changes a row (the rate counters aside); a refused one writes its denial to the audit log."

**C9 — dotenv-format-v1.md:5.** Claim: "anything two dotenv loaders could read differently is rejected on the way in." The import accepts values a pinned loader reads differently and reports them as loader warnings (`dotenv-format-v1.md:142`; `tests/integration/imports/preview.test.ts:302` "loader warnings name the key"; `apps/web/src/screens/import.tsx:144`). Proposed: "…syntax two loaders could read differently is rejected on the way in; a value another loader would read differently is accepted and named in a loader warning; the way out has exactly one spelling."

**C10 — start-here.md:5.** Claim: on production "everything after step 1 is the same." On production the owner sets the password in the bootstrap and enrols after signing in ("Set up an authenticator"), not on the reset page of step 2, and the first sign-in is through `tunnel verify` while the gate is closed (`production.md:89-97`). Proposed: "On production the first account is made by the operator's bootstrap, and you enrol after your first sign-in through the operator's private link (`production.md`, "The first opening"); from step 3 on everything is the same."

**C11 — apps/web/src/errors/explain.ts:178 and 184, 189 (page text).** (a) `quarantined`: "Nothing can be read or changed until it is opened." Through the verification listener a closed + verifying host serves reads, sign-in and reveal (`service-gate.md:32`), and the owner's journey reveals a secret there and then sees this very text on the refused change (`start-here.md:61`, `production.md:97`). Proposed next step: "…once more in a minute. If the same answer comes back at once, close the form and start the change again."

**C12 — apps/web/src/screens/secrets.tsx:284-285 (page text).** Claim: "a value is read from the secret store when you press Reveal on a secret's page, and at no other time."
