Stated limits that are wrong or understated:

- `docs/auth-route-contract.md`: "locked for 900 s after 5 failures" understates the real bound (R1-1).
- `known-limits.md`: it has no entry on the throttle at all (R1-5).
- `known-limits.md` line 35 says "the token works once, for 15 minutes". For an `mfa` link this understates the risk: whoever reads a pasted, still-unused `mfa` link takes the account with no second factor (new password plus their own authenticator).

### 2. Answers

1. Can a password alone reach any product route? None found. Every product route requires an `mfa_complete` session (`authenticateHuman`), and `/v1/auth/sessions` and the like do too. By design, whoever holds the password of an `enrollment_pending` account (a fresh bootstrap) can enrol a factor first.
2. Can any path create an account or switch a factor off? None found. Sign-up and every other native route answer 404, `api_runtime` cannot insert users, and only an operator-issued `mfa` link retires a factor. R1-2 is the reverse case: the restore does not switch the restored factor off.
3. Can a TOTP step, a recovery code or a reset link work twice, across two processes? None in live operation. A used step has a unique row, a recovery code is consumed with a conditional UPDATE, and a reset token is locked FOR UPDATE and consumed. After a restore, R1-2 makes consumed or replaced recovery codes and the old seed work again.
4. Does an expired link or session come back to life? None found. Every limit is judged on database time, an expired session is deleted when it is seen, an expired reset link loses its verifier, and rotation and step-up keep `authenticated_at`. (R1-2 revives restored factor material, not links or sessions.)
5. Can polling keep a session alive? None found. Only `POST /v1/session/activity` moves the idle limit, and the page sends it on a key or the pointer at most once a minute. A client that scripts it reaches the 12 h absolute cap, as the spec allows.
6. Can the throttle be passed by a second process or source? A second process: no, because the counters are in the database. A second source: R1-1 (concurrent attempts from many sources go past the account lock) and R1-5 (lockout as a denial of service).
7. Does any answer, or its timing, say whether an address exists? The answers do not. Timing: R1-4, plausible and small.
8. Is a token, a code or a link in a log, a URL or an audit row? None found. The request log has the route pattern only. The reset token is in the fragment and in a 0600 file. Audit rows hold only a reason, phase or kind. The database holds HMAC verifiers, never raw tokens or codes.
9. Can a sensitive action run without a fresh code? None found. The four starts of FR-1.77 (export, credential issuance, password change, recovery regeneration) check a TOTP verification on database time, bound to the session and its active enrolment. A replay of a stored issuance answers without one, as the spec allows.
