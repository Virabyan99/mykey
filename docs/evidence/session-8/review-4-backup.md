### 2. Answers

1. **A pair eligible without its checks:** no. Read-back digest, `restic check` exit 0 with "no errors were found", the scratch-restored digests and the reduction check all come before signing. A bucket `eligible.json` can outlive a failed commit, but only after every check passed (finding D).
2. **A capture holding two stores that disagree:** no new finding. The only way is the accepted race of finding C, which the restore's reset by class neutralises. An uncertain secret write keeps its effect slot, so the drain refuses to capture.
3. **A restore trusting an old session, password, factor or token:** sessions, passwords, tokens, secret ids and root tokens are not trusted. Factors are: R4-1.
4. **The gate opening without a fresh report of this host, incarnation and build:** no. The report must match `host.env`'s instance id and incarnation and the build, be under 30 minutes old and have every check `ok`. The standalone open refuses restore reports and rechecks four store checks. `--owner-confirmed` turns only the journey checks `ok`. The rule for a host with no secret applies only to an empty `secret_index`. Gaps: R4-7 (deploy path) and R4-11 (replay within 30 minutes).
5. **A secret in pair metadata, a unit file or a journal:** none found. Only R4-9, an environment variable.
6. **Retention deleting the newest eligible pair:** no. The plan keeps it even when it has expired. Only a manual `--delete-orphans` after a same-host restore can delete it.
7. **Session 6's C, D and I:**
   - **C** is rightly accepted. Its effects are reductions that `restoreInvalidate` resets by class.
   - **D** is rightly accepted in substance: such a pair passed every check. Its stated reason "the operator chooses" is wrong for `--newest` (R4-12).
   - **I** is rightly accepted as availability only. While the UPDATE waits, the 30 s drain deadline is not enforced.
8. **The loss of the seal key reported as recoverable:** never in words (`kms-and-unseal.md` says "None"). But it is never measured either, so eligible pairs keep being reported after it is lost (R4-5).
9. **Something needed for a restore kept only on the host:** for an existing pair, no. The KMS certificate key stays on the host by design and is reissued from a new CSR. Two cases fail: an in-place restore leaves the new init answer only on the host (R4-10), and after a restore the later pairs need a root token that exists nowhere (R4-2).
