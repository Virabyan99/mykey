What the tests prove:

- **Migrator.** A fresh database gets every migration, each recorded with its name and SHA-256 and `applied_by = migration_owner`. A second run applies nothing. Two migrators started together both finish and each migration is recorded once. An edited applied file throws `MigrationChecksumMismatch` and changes nothing. A migration that fails half-way leaves no table and no history row, and succeeds after the file is fixed. A new file that sorts before an applied one, and an applied file that has disappeared, are both refused.
- **Privileges.** 58 statements run as the four runtime roles, each expecting success or SQLSTATE `42501`: `api_runtime` can insert and read but cannot run DDL, cannot change a namespace or an operation's key, cannot update, delete or truncate audit events, cannot read the migration history; `provisioner_runtime` can mark an environment ready but cannot read the secret index, memberships, machine credentials or audit events; `backup_reader` reads every table and writes nothing; `maintenance` deletes audit events and cannot run DDL. A new role with no grants cannot connect.
- **Catalog sweep.** Every table in the database is in the test's expected-grants matrix (a new table without an entry fails). For all 20 tables × 5 grantees (four roles and `PUBLIC`) × 8 privileges, and for every column × UPDATE / SELECT / INSERT / REFERENCES, the catalog equals the matrix. `PUBLIC` has nothing, on any table, schema, sequence, or the database. Every table, schema and the database are owned by `migration_owner`. No role has superuser, create-database, create-role, bypass-RLS or replication, and none is a member of another. A table created later is readable by `backup_reader`, writable by `api_runtime` only in `auth`, and a function created later is not executable by `api_runtime`.
- **Tenancy.** Rows that mix two organizations are refused by foreign keys (`23503`): environment ↔ project, secret index ↔ environment, machine credential ↔ environment, access grant ↔ project, environment or member. A grant with both or neither target fails its check (`23514`).
- **Constraints.** One `service_control` row; duplicate effect slot and duplicate operation key fail; the seven operation states and no other; name patterns at their length boundaries (63/64, 128/129, 64/65 code points, NFD rejected); size bounds; no column named `token`, `value`, `secret` or `password`; every `id` is a uuid without a default; no timestamp without a time zone; nothing in schema `public`. The patterns in the database are read from `@mykey/contracts`, and a test compares them.

## Deviations and decisions

- **Roles are server-wide, so one transaction with a lock.** `applyRoles()` locks the role catalog (`pg_authid`) for its transaction. Without it, two test suites setting passwords at once fail with "tuple concurrently updated". A test runs two calls together.
- **`applyRoles()` also makes `migration_owner` the owner of the database it connects to.** The plan's interface has no other place for it, and the migrations need it.
- **Passwords are sent as SCRAM verifiers computed in the client**, so a plain password is never in a statement and cannot reach the server log. Passwords must be at least 16 printable ASCII characters.
- **Test role passwords are derived per stack, not per database.** The plan says "random per database", but a role has one password for the whole server and the suites run in parallel. They are derived from the stack's random superuser password.
- **`db:check` does not use `git diff`.** The plan's form (`drizzle-kit generate` then `git diff --exit-code`) writes into the working tree and fails on any uncommitted migration, so `check` could not run before a commit. The script generates into a temporary copy and reports what would change.
- **drizzle-kit exits 0 when it crashes.** The first version of `db:check` passed while drizzle-kit had failed on an absolute output path; a deliberately added column was not reported. The script now requires drizzle-kit's own completion message, and a test feeds it a doctored snapshot and expects drift.
- **Schema `meta` is created by the migrator**, before the first migration, so `meta.ts` is not given to drizzle-kit. Schemas `auth` and `jobs` are declared in `schema/reserved.ts` and created by `0000_base.sql`.
- **The single `service_control` row is inserted by `0001_grants.sql`**, because the generated `0000` file is not edited.
- **`api_runtime` may not update primary-key columns either**, in addition to the plan's list of identity columns (for example `secret_index.name`).
- **The migrator refuses out-of-order and missing files.** Not in the plan's test list; both would otherwise produce a database that no directory describes.
- **The forbidden-component check now reads installed packages only.** `drizzle-orm` names `@upstash/redis` as an optional peer; nothing installs it, but the old substring search failed on the word. Test added first.
- **`esbuild`'s install script is listed as ignored** in `pnpm-workspace.yaml`. No dependency install script runs in this repository.
- **Two test mistakes fixed during the run:** a count of `id` columns (14, not 15) and a regular expression that lost its backslashes.
- `createPool()` uses a 10-second connect timeout. The 2-second pool-acquire deadline of Document 06 §11 belongs to the API wiring in Session 2.
