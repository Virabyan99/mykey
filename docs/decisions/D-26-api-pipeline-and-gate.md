# D-26 — API pipeline, error mapping, logger and gate record

**Date:** 2026-11-12

**Status:** DECIDED in the Session 3 plan (P-40 … P-44), recorded by the executing agent in Run 3.1. Evidence: `tests/integration/api/{pipeline,routes-mounted,gate}.test.ts`, `tests/unit/api/{log,body,respond,gate}.test.ts`, `tests/integration/audit/append.test.ts`, `tests/integration/jobs/{outbox,privileges,dispatcher}.test.ts`, `tests/staging/api.staging.test.ts`, `docs/evidence/session-3/run-3.1.md`.

## Decision

- **One registration point (P-40).** Every HTTP route of the API is mounted by `mountRoute` from its `RouteDef` in `@mykey/contracts` (method, path, body and query schemas, response schemas, error list). Every contract route is mounted from Run 3.1 on; a route without a handler passes every check and then answers `404 not_found`. A test lists the routes of the Hono app and fails on any other. Test-only routes enter through `AppDeps.test`, which `server.ts` never sets.
- **No 500, 413 or 415 and no new code (P-41).** An oversized, mistyped or unparsable request is `400 malformed_request`; a value of the right shape that breaks its rule is `422 validation_failed` (Zod `invalid_type` and `unrecognized_keys` are shape errors). An unexpected exception answers `503 dependency_unavailable` and logs `{event:"unhandled", errorClass}`; a handler code the route does not list answers the same and logs `unlisted_error`; output that fails its response schema is never sent (`output_invalid`). Messages come from one table keyed by code. Every response carries `Cache-Control: no-store` and the API's own `x-request-id` (a client's is ignored).
- **Body rules.** `body.ts` is the only place a body is read: header block over 16 KiB, a body over the route limit (from `Content-Length`, or by counting while reading — the read stops within one chunk of the limit), a wrong `Content-Type`, a body on a route that takes none, invalid UTF-8, invalid JSON, depth over 16 and duplicate keys (a scanning pass before `JSON.parse`) are all `400`. Node's own header limit is raised to 64 KiB so the pipeline, not Node, answers. **Amendment (Run 3.1 ruling):** a body whose declared length is over the limit is refused from the header, but up to 4 MiB of it is read and dropped before the answer, because a peer that is still uploading otherwise sees a TCP reset instead of the 400.
- **Logger (P-42).** Typed entries only (`request`, `health_down`, `gate_closed`, `unhandled`, `unlisted_error`, `output_invalid`, `outbox`, `listening`, `startup_refused`); the request entry carries the route pattern, never the URL or query. A second pass replaces any key named `authorization`, `cookie`, `set-cookie`, `password`, `token`, `code`, `secret`, `value` or `link`, at any depth and case, with `"[redacted]"`. pino is not used (amends Doc 06 §12). A start-up refusal is one line naming the missing setting, never its value.
- **Gate record v1 (P-43).** `/etc/mykey/gate/gate.json`, root-owned 0644, directory mounted read-only at `/run/mykey/gate`; `{"version":1,"state":"open"|"closed","gateEpoch":n,"hostInstanceId":"<uuid>","writtenAt":"<iso>"}`, at most 4,096 bytes, strict. Opened afresh for every request (`O_NOFOLLOW` on Linux, `lstat` elsewhere); closed with a cause for missing, unreadable, invalid (incl. symlink, directory, size), unknown version, another host, or `closed`. The gate is the first step of every request, matched or not; `GET /health` reports a closed gate as `503 down` (cause `gate` in the log). `host.ts <host> gate open|close|status` replaces the file atomically (temporary file, fsync, rename, fsync of the directory), epoch + 1; `host.ts up` writes `MYKEY_HOST_INSTANCE_ID` once and never writes a gate record, so **every deploy starts closed**.
- **Audit (P-44).** `@mykey/audit` exports `appendAudit` over a closed list of actions, each with a strict `details` schema of ids, enums, integers, booleans or short patterned strings; actor, target, organization, request and operation ids must be UUIDs. It writes inside the caller's transaction when given one; a failed insert is `AuditUnavailable` → `503 audit_unavailable`, and the action does not happen.
- **Jobs.** pg-boss 12.38.1 in schema `jobs`, created by migration `0004` from pg-boss's construction plan (without its own BEGIN/COMMIT; `pnpm run jobs:check` compares). Runtime instances never create or migrate; queues are created by `ensureQueues` as `migration_owner` (`db:migrate`, `host.ts db-init`, the harness). A job's data is exactly `{ operationId }`. The API's outbox dispatcher runs once at start and every second; the send is part of the dispatcher's transaction, so a crash before commit leaves neither a delivered row nor a job.

## Grants found (Run 3.1 Task A)

`api_runtime`: `USAGE` on `jobs`, `EXECUTE` on `jobs.job_now()`, `SELECT` on `jobs.version`, `jobs.queue`, `SELECT, INSERT` on `jobs.job`, `jobs.job_common`. `provisioner_runtime`: the same usage, function and reads, and `SELECT, UPDATE, DELETE` on the job tables (no `INSERT`: it never creates a job; `DELETE` is for its supervisor's clean-up). Each was found by removing it and watching a test fail, except `DELETE`, kept for the documented supervisor behaviour. No runtime role needs DDL. `maintenance`: `INSERT` on `audit.event`, `auth.user`, `auth.account`, `auth.account_state`; `UPDATE (state, auth_epoch, credential_epoch, updated_at)` on `auth.account_state`; `DELETE` on `auth.session`; `SELECT` on every `jobs` table.

## Consequences

- The full order of Doc 06 §4.4 (mixed credentials, Origin, authentication, ancestry, visibility, action, state, freshness) is added inside `mountRoute` by Runs 3.4–3.7; nothing else changes the frame.
- pg-boss creates a `jobs.queue_stats_YYYYMMDD` partition for the day of installation and the next; the privilege matrix treats them as `jobs.queue_stats`. Queue statistics are off, so no later partition is created at run time.
