# D-19 — Auth storage design

**Date:** 2026-11-11

**Status:** DECIDED by the executing agent in Run 2.3, on measurements against better-auth 1.7.19 and PostgreSQL 18.6 (local stack). Evidence: `tests/unit/auth/*.test.ts`, `tests/integration/auth/*.test.ts`, `docs/auth-route-contract.md`, `docs/evidence/session-2/run-2.3.md`.

**Verdict (G-AUTH): GO.** The first design holds; the Doc 10 §8.1 fallback (Better Auth for password verification only, a product-owned session table and cookie) is not taken.

## Decision

- **P-24 — no stock two-factor plugin.** Better Auth keeps password verification and sessions. TOTP, recovery codes and factor state are product-owned in `packages/auth/src/factors/`. The stock `twoFactor()` plugin was installed on a throw-away instance and fails three contract rules on 1.7.19, each proven present by `stock-plugin.test.ts`: a TOTP code completes sign-in twice inside its window; the backup codes are stored as one list that `symmetricDecrypt` opens with the server secret; `trustDevice: true` in a request body sets a 30-day trust cookie.
- **P-25 — explicit routes.** No Better Auth catch-all handler is mounted. Five native endpoints are served, each from its own route through `auth.api.<name>({ …, asResponse: true })` with a strict body: `POST /sign-in/email`, `POST /sign-out`, `GET /get-session`, `POST /change-password`, `POST /revoke-sessions`. The other 27 (method, path) pairs of 1.7.19 are listed by name and answer the contract's `404 not_found`; a version that adds a route fails `routes.test.ts` until it is placed. No response body carries a `token`. Origin checking (Run 3.7) and throttling (Run 3.3) are the product's, because `auth.api` bypasses Better Auth's own; Better Auth's `disableOriginCheck` and `disableCSRFCheck` are still set to `false` explicitly (both default to `true` under a test environment).
- **Factor routes** (an addition to the route set of D-15, which left auth routes to this run): `POST /v1/auth/totp/enroll`, `/totp/activate`, `/totp/verify`, `/recovery/verify`, `/recovery/regenerate`. Their bodies, answers, cookies, account states and session phases are in `docs/auth-route-contract.md`, which also settles the cookie name left open by D-15: `__Secure-better-auth.session_token` (`Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`).
- **P-26 — keyed verifiers.** `auth.session.token` holds `v1.<keyId>.<base64url(HMAC-SHA-256(lookup key, raw token))>`; there is no ciphertext copy, and a check constraint refuses any other value. Better Auth reaches the table only through `protectedAdapter`, which rewrites `token` in written data and in `token =` / `token in` lookups (to the verifiers of every key of the ring, so a rotation keeps old sessions until the old key is removed), returns the raw token only on rows found by token, and throws `UnsupportedTokenOperation` for any other use of `token`. The four token paths of 1.7.19 (`create`; `findOne`, `findMany`, `delete` by token) are committed in `storage.test.ts`; nothing below the wrapper ever saw a raw token.
- **Second factor.** The seed is 20 random bytes stored only as a compact JWE (`dir`, `A256GCM`, `jose`) whose protected header carries `kid`, `purpose: "totp-seed"`, `sub` and `enr`; decryption refuses another user or enrollment. TOTP through `otpauth`: SHA-1, 6 digits, 30 s, ±1 step. Recovery codes: ten codes of 20 symbols from a 32-symbol alphabet (100 bits), shown as four groups of five, stored as `HMAC-SHA-256(recovery key, enrollmentId || code)`. Every factor step is one transaction: lock `account_state`, then the session row; check state, epoch and expiry; match the step (−1, 0, +1, without looking at used steps); insert the used step (a unique violation is a replay) or consume the code (`UPDATE … WHERE consumed_at IS NULL`); replace the session by a new `mfa_complete` row with a new token and the same `authenticated_at`; commit; only then sign the cookie with Better Auth's `makeSignature` and its own cookie settings.
- **Database.** Migration `0003_auth_base.sql`: schema `auth` with Better Auth's `user`, `session`, `account`, `verification` (snake_case, uuid ids without default) and `account_state`, `totp_enrollment`, `totp_step_used`, `recovery_code`; `app.membership.user_id` → `auth.user(id)` (P-14). `api_runtime` updates column by column as in schema `app` (never `id`, `user_id`, `created_at`, a stored verifier or `authenticated_at`); it cannot delete a used step or a recovery code, and may update only the two consumption columns of a code. `maintenance` reads schema `auth` only. The OAuth token columns of `account` exist because the library's schema names them; a check keeps them empty, and `provider_id` must be `credential`.
- **Libraries.** better-auth 1.7.19 (1.7.20 was one day old), jose 6.2.17, otpauth 9.6.0. No open advisory for any of them; `pnpm audit` reports one moderate esbuild dev-server issue reached through better-auth's peer dependency on drizzle-kit, a build tool that is never served.

## Observations that later runs build on

- **Password change replaces the session.** `change-password` with `revokeOtherSessions: true` removes every session of the user and sets the cookie of a new `password_verified` session (`totp_verified_at` and `enrollment_id` empty). It fails closed — the owner passes the factor again — and is pinned in `storage.test.ts`. Runs 3.4 and 3.5 decide whether to re-elevate inside the same transaction or rebuild the route.
- **Sign-in does not look at `account_state`.** A `disabled` or `recovery_pending` account can still pass the password today; Run 3.4 adds the check. Factor steps already require the right state.
- **Session epoch.** A new session takes `auth_epoch` 0 from the column default; elevation requires it to equal `account_state.auth_epoch`. The run that first bumps an epoch must also set it at sign-in.
- **Logging.** No parameter is logged (`log_parameter_max_length*` = 0, as on the hosts). A statement whose error message echoes a value (a cast error, a check-constraint `DETAIL`) would still put that value in the log; the wrapper's job is that no raw token ever reaches a statement.

## Runs that change under a fallback

None: the verdict is GO. Had the fallback been taken, Runs 3.2, 3.4, 3.5, 3.6 and 7.2 would have changed.

## Cost if wrong

A Better Auth upgrade that adds a token path or a route is caught by `storage.test.ts` and `routes.test.ts` before it ships; the session table refuses a raw token outright. If the wrapper approach ever has to go, the fallback design replaces `auth.ts`, `routes.ts` and the adapter, while the factor module, the tables and the contract stay.
