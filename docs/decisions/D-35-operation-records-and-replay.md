# D-35 — Operation records, replay by state, status and expiry

**Date:** 2026-11-13

**Status:** DECIDED in the Session 4 plan (P-63, P-64, P-65, P-80, P-83), recorded by the executing agent in Run 4.1. Evidence: `tests/integration/operations/{records,replay,status}.test.ts`, `tests/unit/operations/replay.test.ts`, `tests/unit/api/respond.test.ts`, `tests/integration/authz/matrix.test.ts`, `docs/evidence/session-4/run-4.1.md`.

## Decision

- **Scope of an operation.** `app.operation` gains `project_id`, `environment_id`, `secret_name` (checked against the secret name pattern) and `parent_operation_id` (migration `0011`), written at insert only. Existing rows were backfilled from `target`. `target` stays the deepest scope id of the path.
- **Intent.** The fingerprint's canonical text gains `params`: the path parameters other than `org`, `project`, `env` (`name`, `preview`, `operation`, `credential`), only when there is at least one — fingerprints stored before Run 4.1 still match. `intentOf` in the pipeline is the one place target and params are derived. Without it, `PATCH …/secrets/A` and `…/secrets/B` with one key and one body would have replayed each other.
- **Replay answers by stored state** (`replayAnswer`): `accepted`, `executing`, `awaiting_input` → 202 with the envelope; `succeeded` → the route's 201 or 200; `partial` → 200; `rejected` → its stored error code with `operationId` (an error code the route does not list answers `dependency_unavailable` and logs `unlisted_error`); `uncertain` → `503 outcome_unknown` with `operationId`; a terminal row whose `replay_expires_at` has passed on database time, or a tombstone → `409 replay_expired`. The expiry check comes before the fingerprint comparison, because an expired row has lost its fingerprint. Unfinished rows never expire. The envelope of a rejected operation carries `result: { errorCode }`; an uncertain one carries no result.
- **The record's transitions.** `claimDispatch` moves `accepted → executing` once, for its own boot id, and is the dispatch marker. `finishOperation` is one conditional update (`executor_boot_id` and `state IN (accepted, executing)`): another boot id or a terminal row changes nothing and answers null. `succeeded`, `partial`, `rejected` set `completed_at` and a replay expiry of 30 days on database time; `uncertain` and `awaiting_input` set neither. `touchOperation` moves the heartbeat only for the owner.
- **Expiry.** `ops operations-expire` (as `maintenance`, one transaction, one audit row `operator.operations_expire { expired }`) writes a tombstone for every expired terminal row and clears its `fingerprint`, `fingerprint_key_id`, `expected` and `result`; the row stays for attribution and the audit link. `api_runtime` lost `INSERT` and `UPDATE` on `app.operation_tombstone` in migration `0011` (the plan said "no grant changes"; its own test needed the API to be unable to expire — ruling recorded in the run note). Its timer is Run 6.9.
- **Status visibility.** `operations.get` and `operations.list` take `action: null` (state class `metadata_read`), so status stays readable while a project or environment is in review; an organization in review answers `503 backend_inconsistent` (both codes were added to `operations.get`'s list). Scope `operation` reads the row and the caller's authority on its organization, project and environment on every request: an owner or admin sees it; a member sees it only when it is its own and `decide` still allows that member the action of the route that made it (`resources.manage` when no route has that id). Every other case — another member's, another organization's, an operator's, a non-UUID, an absent id — is the same `404 not_found`.
- **The list** shows the environment's operations without children, newest first; a member sees only its own, an owner or admin all (`mine` marks the caller's). The first page's first row is the anchor of every later page (microseconds since the epoch in the cursor's generation field), so new operations never appear in a paging run and the list never answers `listing_changed`.
- **Errors** carry `operationId` for any code and `details` from an allowlist only: `version_conflict` → `{ currentVersion, currentStateTag, state }`, `capacity_exceeded` → `{ limit }`. Details that fail their schema are dropped and logged `output_invalid`.
- **The pipeline matrix** runs every contract route through the harness stub (`stubs: "all"`, P-80); real handlers are covered by `matrix-live.test.ts` in Run 4.9.
- **Provisioning (carried):** the queue `environment.provision` expires a held job after 120 s (`expireInSeconds`, set on an existing queue by `updateQueue`), so a job of a killed provisioner is taken again within about two minutes; activation succeeds only while the operation is still this worker's and `executing` and the environment still `pending` — otherwise the operation goes to `awaiting_input` (`state_conflict`) and nothing activates.

## What would change this decision

- Machine principals (Session 5) need their own visibility rule for `operations.get`.
- If replay records must survive longer than 30 days, `LIMITS.operation.terminalRetentionDays` changes, not this design.
