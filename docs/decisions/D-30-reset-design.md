# D-30 — Operator reset of a lost password or second factor

**Date:** 2026-11-12

**Status:** DECIDED in the Session 3 plan (P-51), recorded by the executing agent in Run 3.6. Evidence: `tests/integration/ops/{reset,output}.test.ts`, `tests/integration/auth/{reset,reset-race}.test.ts`, `docs/evidence/session-3/run-3.6.md`.

## Decision

- **Only the operator starts a reset** (`ops reset-account --email <address> --kind password|mfa`, as `maintenance`; `initiateReset` in `@mykey/auth/operator`). No HTTP route initiates anything. One transaction: lock the account → `recovery_pending`, `auth_epoch + 1` → delete every session → supersede every open token (its verifier set to NULL) → insert the new token → audit `operator.reset_initiate` (`{ kind }`). After the commit the throttle locks of the account (e-mail and user id, every phase) are cleared, so a locked-out owner can complete the reset.
- **Storage.** Table `auth.reset_token` (migration `0006_reset`): id, user, `verifier` = `HMAC-SHA-256(reset key, token)` with its key id, kind, created, `expires_at` (`now() + LIMITS.reset.linkSeconds`), `consumed_at`, `superseded_at`. The token is 32 random bytes, base64url (43 characters), never stored. The verifier is set to NULL at consumption, at supersession and — by the API's session clean-up — once expired. Column `auth.session.reset_token_id` marks a reset challenge. Grants: `api_runtime` reads and may set `verifier, consumed_at`; `maintenance` inserts and may set `verifier, superseded_at`.
- **The link** is `${baseUrl}/reset#t=<token>&k=<kind>`: the token travels in the fragment, which no server receives. The command writes it to `~/.mykey/out/<timestamp>-reset-link` (0600) and prints the path and the expiry, never the link. The reset page (Run 7.x) must read the fragment, clear it from the address bar and send no referrer.
- **Completion** is the contract route `POST /v1/auth/reset/complete` (class `reset_flow`): body `{ token (43 characters), newPassword (P-46), code? }`, answer `200 { next: "sign_in" | "enroll" }`. A password outside the rule is `422` from the schema before the token is looked at. Steps: `admit("reset", source)` → the token's row by verifier under every key of the ring, locked; it must be unconsumed, not superseded, not expired (database time), and its account `recovery_pending`.
  - **`password`**: a factor code is required, under the `factor` throttle of the user: a TOTP step (used once) or a recovery code (consumed) of the active enrollment. Wrong → the failure is counted and the token stays open. Right → new hash, `credential_epoch + 1`, `auth_epoch + 1`, account `active`, token consumed, every session deleted, audit `auth.reset_complete` → `next: sign_in`, no cookie.
  - **`mfa`**: the active (and any pending) enrollment is retired with its seed erased and its recovery codes consumed; new hash, `credential_epoch + 1`, token consumed, every session deleted; the account **stays** `recovery_pending`; one challenge session (phase `enrollment`, `reset_token_id` set) → `next: enroll` with its cookie.
  - Every failure — unknown, expired, superseded or consumed token, missing or wrong code, wrong account state — is the same `401 unauthenticated`, audited as `auth.reset_failed` with the reason.
- **The challenge session** is admitted by `resolveSession` while its account is `recovery_pending`, its epoch matches, and `now()` is before the lesser of `authenticated_at + 10 min` and the token's `expires_at`. It reaches `/totp/enroll`, `/totp/activate` and `/sign-out`, and nothing else (`get-session` answers 401 for it). Activation makes the enrollment active, returns ten new recovery codes once, makes the account `active`, raises `auth_epoch` and deletes every session including the challenge: the user signs in afresh.
- **While `recovery_pending`** no password signs in — neither the old one nor, in the `mfa` flow before activation, the new one. Keeping the account in that state until activation is what makes the new password unusable before enrollment, without a second password column.
