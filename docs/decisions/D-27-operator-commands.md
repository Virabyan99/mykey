# D-27 — Operator commands, `maintenance` rights, password rule, session cookie

**Date:** 2026-11-12

**Status:** DECIDED in the Session 3 plan (P-39, P-45, P-46), recorded by the executing agent in Run 3.2. Evidence: `tests/integration/ops/{bootstrap,output}.test.ts`, `tests/unit/ops/{cli,output}.test.ts`, `tests/unit/auth/{keys,routes}.test.ts`, `tests/integration/auth/{sign-in,routes}.test.ts`, `tests/integration/database/privileges.test.ts`, `tests/unit/skeleton/skeleton.test.ts`, `tests/staging/api.staging.test.ts`, `docs/evidence/session-3/run-3.2.md`.

## Decision

- **Operator commands live in `apps/ops` and run on the workstation** (P-45). `node scripts/host.ts <host> ops <command…>` opens the PostgreSQL tunnel, logs in as `maintenance` (password kept on the workstation only) and calls `runOps` in-process. A command never takes a secret as an argument (any flag named like one is refused, exit 64), reads secrets from stdin, and writes secret output only to `~/.mykey/out/<utc-timestamp>-<name>` (0600 under 0700), printing the path. The SSH, redaction, hosts-file, tunnel and status code moved from `tests/harness/staging.ts` to `apps/ops/src/remote` (`@mykey/ops/remote`); the harness re-exports it, and `scripts/host.ts`, `scripts/probe.ts` and `scripts/require-staging-env.ts` import it from there (closes M17).
- **Account code only an operator may run is `@mykey/auth/operator`** (`bootstrapOwner`; Run 3.6 adds the reset). A unit test walks the import graph from `apps/api/src/server.ts` and fails if it reaches `packages/auth/src/operator/`, `packages/openbao/src/admin.ts` or `apps/ops`.
- **`maintenance` rights** (migration `0004`): `INSERT` on `audit.event`, `auth.user`, `auth.account`, `auth.account_state`; `UPDATE (state, auth_epoch, credential_epoch, updated_at)` on `auth.account_state`; `DELETE` on `auth.session`. It cannot change a stored hash or a session, or delete a user. `maintenance` is also the identity that records a reconciliation (the open question of Run 4.5), unless that run finds a reason against it.
- **`api_runtime` cannot create accounts** (migration `0005`, a finding of Run 3.2): `INSERT` on `auth.user` and `auth.account` is revoked. No API path creates an account (FR-1.01), and the plan's test "`api_runtime` cannot run the bootstrap" needed it. The plan's later migrations shift by one (`0006_reset`, `0007_review_reason`, `0008_resource_generation`).
- **The bootstrap** is one transaction under `pg_advisory_xact_lock(hashtext('mykey.bootstrap'))`: an active owner with the same e-mail → `already_present`, nothing changes (the password included); another e-mail → `refused`; otherwise user, credential account (Better Auth's hash), account state `enrollment_pending`, organization `provisioning`, owner membership, audit `operator.bootstrap`. E-mail addresses are stored trimmed and lower-cased, as Better Auth looks them up.
- **Password rule (P-46):** 12 to 1,024 characters (code points) and at most 1,024 UTF-8 bytes, checked by the product (`checkPassword`); Better Auth is configured with `minPasswordLength: 12`, `maxPasswordLength: 1024` (its default maximum, 128, would refuse passwords the limit allows).
- **Session cookie (P-39):** Better Auth's name `__Secure-better-auth.session_token` with `SameSite=Strict`, `Secure`, `HttpOnly`, `Path=/` and no `Domain` (host-only), set through `advanced.cookies.session_token.attributes`; `__Host-` is not used (in 1.7.19 the cookie getter can only prefix `__Secure-`). One helper (`sessionCookie`) writes every Set-Cookie of a session, at sign-in (`Max-Age=43200`) and at factor elevation.
- **Key rings:** eight rings (`cookie`, `session-lookup`, `seed-encryption`, `recovery-verifier`, `rate-limit`, `reset-verifier`, `replay-fingerprint`, `cursor-mac`), key ids `k<positive integer>`, the current key the greatest number (closes M15). Any other `.key` file name is a start-up error naming the file. `host.ts <host> keys init` creates the missing rings on the workstation and installs the missing files on the host, so later runs never touch host custody again.
- **Sign-in on the pipeline:** the API answers `200 {"phase":"password_verified"}` with the cookie, and the same `401 unauthenticated` (no cookie, no session) for an unknown e-mail, a wrong password, a `disabled` or `recovery_pending` account and an epoch that moved during the sign-in. `authenticated_at` and `last_user_activity_at` come from the database's `now()` (Better Auth's API-clock defaults removed). The auth routes use the API's envelope builder, request id and body reader; without a throttle they refuse to mount (the harness passes `allowUnthrottled: "test"` until Run 3.3).
